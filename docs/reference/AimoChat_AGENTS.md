# AimoChat 项目规则

## 文档职责

- `README.md` 只负责当前项目概览、启动方式和文档导航，不承载完整历史或已经完成的阶段计划。
- `CHANGELOG.md` 是版本历史真源；历史行为与版本变化从这里追溯，不把旧版本说明继续复制到 README。
- `DESIGN_SYSTEM.md` 是当前 UI / UX 的单一设计真源。
- `DESIGN_REFRESH.md` 是归档的视觉改版背景，只用于追溯，不需要随当前设计变化持续更新。
- `package.json` 与 `client/package.json` 的版本号表示当前产品版本，应与 README 和 CHANGELOG 顶部版本保持一致。

## 必读设计规范

- 任何涉及 **UI / UX / 主题 / 响应式 / 动效 / 骨架屏 / 组件样式 / 管理后台界面** 的任务，在修改代码前必须先阅读根目录 [`DESIGN_SYSTEM.md`](DESIGN_SYSTEM.md)。
- `DESIGN_SYSTEM.md` 是现行视觉与交互规范的单一设计真源；`DESIGN_REFRESH.md` 仅作为历史改版背景，不得用其中旧描述覆盖现行规范。
- 若本文的工程 / 安全 / 业务硬规则与设计文档冲突，以 `AGENTS.md` 的硬规则优先；纯视觉与交互冲突以 `DESIGN_SYSTEM.md` 为准。
- 不得只复制当前某个页面的局部样式作为新规范；先查 Design System、全局 token 与统一组件，再决定是否需要新增。
- 用户可见文案同样属于 Design System：默认“短、有人味、不过度解释”；标题已经说明功能时不重复副标题，复杂内部规则采用 `ⓘ` / 帮助等渐进式披露，但安全、计费、隐私、不可逆、数据丢失与 AI 能力边界不得为了简洁而省略。

## 编码与需求沟通

- 命名遵循项目现有风格，与所在模块保持一致
- 编写代码时保持良好的注释与可读性，说明关键逻辑、设计意图和必要的边界条件
- 对拿不准或未完全理解的需求，主动使用提问工具与用户对齐；问题可以细致、多轮，并纳入用户在回答中补充的需求

## Git 提交

- 修改代码并验证通过后，必须 git 提交到本地；仅审计、报告、说明文档等工作不自动提交。提交前删除不再需要的临时文件（仅本地提交，不推送远端；未经用户明确要求不得 push）
- 提交信息风格沿用仓库现状：`类型(范围): 概要`（如 `feat(auth): ...` / `fix(ui): ...` / `chore: ...`），正文说明动机与关键改动

## 版本管理

- 变更必须记录：当天日期 + SemVer 版本号 + 变更说明，写入 `CHANGELOG.md`
- 根据实际变更决定升级版本号或合并到上一版本的变更记录，无需询问用户
- 版本升级映射：新功能 → 次版本，细节/修复 → 修订号，不兼容 → 主版本
- 每次版本变化同步更新 `README.md`、根 `package.json` 与 `client/package.json` 的当前版本号；`CHANGELOG.md` 顶部必须存在同一版本的记录
- README 只展示当前版本，不复制历史版本列表；历史变化统一链接到 CHANGELOG
- 版本号不显示在应用界面中
- 基线：2026-08-22 为 `1.0.0`


## 平台工程与客户端边界

- `client/` 是当前唯一 Web 业务 UI 真源；`android/` 不得复制 `client/dist`、`client/src` 或维护第二套等价 Web 页面。
- `android/` 是正式平台子工程，只承载 Android Shell、WebView 生命周期、局域网发现、Native Bridge、通知、小组件、OPPO / Xiaomi / Android 系统表面，以及未来明确选择原生化的 View 层。
- 跨设备必须一致的权限、账号、计费、Provider、持久化和安全规则放在 `server/`；Android / Web 不得各自复制一份安全裁决。
- 若未来 Android 使用 Compose 或 Desktop 使用独立 UI，优先共享 API / Socket / 数据协议与设计 Token；“平台 UI 不同”不得演变为“业务规则重复实现”。
- 产品版本以根 `package.json` 为唯一真源；`client/package.json` 同步同版本，Android 构建脚本与 Gradle 必须自动读取根版本，不单独手写版本号。
- Android 正式签名、`.env`、`local.properties` 与任何 keystore 不得入库。
- 平台结构或构建脚本变化后运行 `pnpm run platform:check`；涉及 Android 源码时至少完成 Java / Manifest 静态检查，具备 SDK 环境时再构建 APK。

## AimoChat Design System

### 设计方向

- 主应用采用「编辑部 / 档案」式平面设计：纸张白 / 暖灰底色、墨色正文、中性灰层级、清晰分隔线、大字号衬线标题与克制的功能组件；使用低饱和陶土作为有限的交互强调色
- 内容优先。减少传统 SaaS 式的卡片堆叠、无意义渐变、悬浮阴影、过度圆角和装饰性英文编号
- 不为了“统一”抹掉必要语义：头像可以为圆形，消息气泡、开关、Badge、交互画布和移动端抽屉可保留各自形态；禁止的是没有设计语义的新样式变体
- 登录 / 注册 / 忘记密码及直接认证流程（邮件链接状态、注册补全、二步验证）是明确的品牌例外：恢复原版 AimoChat 门禁视觉与暖中性局部交互色，桌面端使用原版圆润卡片，≤768px 按原版规则平铺；这些页面不得继承主应用低饱和陶土作为主按钮 / 链接 / 分段器颜色，但输入框仍禁止聚焦泛光
- 桌面端顶栏左侧不额外显示 `AimoChat` 字样；角色库不要重新加入 `AIMOCHAT / CHARACTER ARCHIVE`、档案编号等装饰文案

### 设计 Token

- 颜色、圆角、阴影优先使用 `client/src/aimo/css/components/base.css` 中的语义变量，不在组件里随意增加硬编码值
- 颜色：正文使用 `--text-*`；主操作、正文链接、可点击强调统一使用 `--accent*` / `--link*`；成功 / 警告 / 危险分别使用 `--success*` / `--warning*` / `--danger*`。不要在组件里另造“另一套主色”
- 圆角：普通控件 `--radius-control`，菜单项 `--radius-item`，普通表面 `--radius-surface`，浮层 `--radius-popover`，桌面弹窗 `--radius-modal`，移动抽屉 `--radius-sheet`
- 阴影：普通页面内容原则上无阴影；浮层使用 `--shadow-popover`；大型模态 / 抽屉仅在确有层级需要时使用 `--shadow-lg`
- `999px` 只用于真正的 Pill / Badge / Switch；`50%` 只用于圆形头像、圆点或明确的圆形控件
- 新增视觉 token 时先判断是否真的无法由现有语义表达；不要因为某一个组件“差 1px”就新增新的全局 token

### 排版与信息层级

- 页面主标题优先使用 `--font-serif`，大页面标题采用约 `36–58px` 的响应式尺度、较紧字距和中等字重
- Section Label 使用 `--section-label-size`、`--section-label-weight`、`--tracking-caps` 和 `--section-label-color`；用于分区标题时保持小号、字距明确、弱于正文标题
- 正文与说明优先通过字号、颜色、留白和分隔线建立层级，不通过新增背景卡片强调
- 角色创建 / 编辑页的自主性强度等选项保留“低饱和陶土描边 + 柔和填充”的选中态，不添加左侧重点条

### 页面与组件

- 角色库 / 创建编辑 / 会话中心 / 关系图谱的大页面标题、留白和分区节奏应属于同一视觉体系
- 会话中心的已有会话优先使用文档式列表和分隔线；创建入口可使用轻描边动作面板，但不要使用 hover 上浮 + 大阴影
- 关系图谱属于交互工作区而不是普通卡片：允许保留画布边界 / 网格，但不要把整个页面包成大白卡
- 设置面板分区 Tab 与偏好页性别分段使用顶栏同款「纸面轨道 + 墨色滑块 + 字形级实时反色」语言（共用 `controls.js` 的 `syncSegmentTextInversion`）；设置面板顶部「偏好设置 / 数据管理 / 问题反馈 / 版权声明」必须使用真实滑动指示器，点击时平滑滑动、鼠标与触屏拖动时跟手预览、松手吸附；管理后台 Provider Tab 等操作型分段器仍保持“描边轨道 + 低饱和陶土选中”，顶部导航、会话分支等结构性导航允许继续使用墨色选中，避免全页面过度强调
- Popover / Select / Menu（头像菜单、角色菜单、自定义下拉、@ 提及、关系详情、输入加号菜单等）统一使用 `--radius-popover` + `--shadow-popover`，内部菜单项使用 `--radius-item`
- 管理后台遵循同一 Design System：页面标题使用衬线层级，统计区与表格以分隔线和信息密度为主，主操作 / 导航强调使用同一低饱和陶土交互色；不要把管理员界面当成无需设计的临时工具页
- 表单输入使用 `--radius-control`；不要在同一页面混用 8/9/10/11px 等无语义差异的半径


### 主题色与交互语义

- AimoChat 的页面骨架仍以纸白 / 墨色 / 中性灰为主；低饱和陶土只承担“可操作性”和少量活性，不作为大面积背景或装饰色。浅色主题 `--accent` 使用压低饱和度的陶土，深色主题提高明度但保持克制
- 所有主要动作按钮、正文链接、可点击文字强调、开关开启态、表单聚焦描边和操作型 Segmented Control 从 `--accent*` / `--link*` 取色；顶部导航、标题、消息内容、分支选中等结构性状态仍优先使用墨色，不把整页染成主题色
- 输入框、Textarea、Select、自定义下拉与聊天输入区的激活 / 聚焦状态**只允许改变描边颜色**，不得使用外发光、聚焦光晕或 `0 0 0 Npx` 式 box-shadow；键盘可访问性焦点环只保留在按钮 / 链接等非文本输入控件上
- 次要 / Ghost 按钮保持中性。危险、成功、警告仍使用 `--danger*` / `--success*` / `--warning*` 的低饱和语义色，这是功能语义例外
- 管理后台不是独立品牌：`client/src/admin/admin.css` 必须与主应用 `base.css` 的纸白 / 墨色 / 中性灰、低饱和陶土及状态色保持同步。后台可保留更高信息密度，但不得发展出另一套 SaaS 调色板

### Markdown 与图片

- AI 消息的 Markdown 在流式生成阶段实时解析，单聊与群聊行为一致；不得出现“生成时纯文本、生成结束突然整体变 Markdown”的双重体验
- Markdown 外链图片允许任意合法 `http` / `https` 图源，不按域名白名单屏蔽；但默认只渲染图片占位，点击前 DOM 中不得出现外链图片的 `<img src>`，避免追踪像素或无意外部请求
- 用户主动点击图片占位后才能真正加载外链图片，并统一进入 AimoChat 图片查看器；查看器同时接管消息区已有附件图片 / 生图结果，支持关闭、上一张 / 下一张、缩放与打开原图
- 外链图片 URL 仍需做协议与属性注入过滤。“不屏蔽图源”不等于放弃 XSS / URL 安全校验

## 世界观、创作 AI 与历史推演

- 顶栏「创造」为常驻入口：创造中心至少包含“创建角色 / 创建世界观”；「活动」为独立常驻入口，当前活动为世界观历史推演
- 世界观是角色扮演的上层事实源。一个角色最多有一个**主世界观**，但可以被其他世界观引用；世界观只保存角色引用与世界观专属身份 / 势力 / 状态，不复制角色本体
- 同世界观角色不得自动获得彼此全部角色卡。默认只注入该角色按知识边界可知的世界身份、状态、势力与关系；秘密、内心、隐藏目标不得因为“同世界观”而泄露
- 世界观信息使用 `public / factions / characters / secret` 可见性。世界观硬规则即使对角色不可知，也可作为作者级运行规则约束模型，但必须明确标记为“不可作为角色知识直接陈述”
- 事实冲突时固定优先级：**世界观硬设定 > 已确认历史 > 势力与角色关系 > 角色自身设定 > AI 临时推断**。低优先级不得覆盖高优先级
- 历史采用“总述 + 结构化事件”。任意已确认事件都可创建 IF 分支；IF 分支可继续产生子分支，但永远是旁支，**不得扶正、不得合并回主时间线**
- 历史推演每次服务端只生成一步，自动 3 / 5 / 10 步由前端连续调用，以保证每一步独立计费、可暂停。推演结果先进入本次候选历史，用户明确提交后才写入时间线
- 历史推演必须使用服务器持久化的**多会话**模型：每条会话创建时锁定活动类型、世界观与主线 / IF 分支，保存日志、候选历史、状态面板、候选角色 / 势力与批准态；刷新、离开或换设备后仍可继续。需要更换世界观 / 时间线时新建会话，不得在原会话中改锁定目标
- 推演自主程度至少包含 `balanced` / `free`：平衡模式遇主要角色死亡、核心势力毁灭、不可逆世界级灾难等重大变化时必须进入批准态；批准前该事件不得进入后续推演上下文、不得更新状态或正式生成实体
- 推演中新出现的角色 / 势力只作为候选，可由用户手动“转换为角色 / 势力”；不得自动创建正式实体
- 可转正角色必须在历史推演的**同一次正常计费调用**中生成完整可编辑角色草案，不得为了补草案在后台偷偷追加一次 AI 调用。草案至少覆盖名称、性别、身份、背景、性格、说话方式、喜恶、价值观、目标、边界，并可带世界身份 / 状态 / 势力与关系建议；后续推演若获得新可靠信息，应按同名候选增量刷新草案，形成整轮推演后的角色设定。点击“转换为角色”只把草案带入正常角色创建流程，仍由用户最终确认
- AI 帮写统一遵循“请求 → 可编辑预览 → 应用 / 取消”。禁止生成后直接覆盖表单；预览允许用户手改，但不提供预览内二次 AI 对话修改
- 世界观 AI 帮写唯一前置必填项是「世界观」核心设定；角色 AI 帮写若已选择世界观，必须读取该世界观并服从事实优先级。已有用户内容优先保留，结构化列表默认追加建议而非整块替换
- AI 帮写与历史推演都走正常模型 Token 计费，不得绕过现有积分 / 免费额度结算链路

## 界面与交互约定

- 弹窗统一使用 `js/dialog.js` 的 `showConfirmDialog`，禁用浏览器原生 `confirm`/`alert`
  - 桌面端：居中模态弹窗
  - 移动端（≤860px）：底部抽屉 + 高斯模糊遮罩
- 按钮点按不出现浏览器默认蓝色焦点框（仅保留键盘 Tab 焦点环）
- 顶栏导航：一级页面直接使用全局顶栏；具体单聊 / 群聊、社区二级页、角色 / 世界观编辑与详情、具体推演会话等上下文页面默认展示局部顶栏，全局栏在同一顶部槽位收起，禁止双顶栏同时出现。局部栏下滑跟手呼出全局栏、全局栏上滑返回局部栏；首次可给一次非阻塞手势提示，成功完成后永久收起。桌面四段式必须保持视口几何居中，窄屏禁止换行，搜索 / 消息临时分段只在空间充足时出现；极窄屏依次把搜索、消息收入头像菜单，不缩小触摸目标
- 所有 N 段式控制器（尤其顶栏与设置分区）统一使用 `js/controls.js` 的 `bindSegmentedControl`：位置与宽度只能读取当前真实 DOM 几何，不得在业务页面保存旧下标、复制 `left / width` 动画或自建拖拽实现。跨不同宽度分段拖动时必须连续插值位置与宽度；桌面与移动端均应支持拖拽，页面重绑事件不得以无动画校准覆盖一次已经开始的点击滑行动画
- 顶栏 N 段式的局部反色文字不得依赖写死白色或 `mix-blend-mode`；底层文字必须保持主题正常颜色，滑块覆盖区只通过统一组件输出的实时几何裁切反色文字层，确保不同主题/浏览器下均可读
- 顶栏白色 / 反相滑块覆盖文字时使用**字形级实时反色**：滑块覆盖到多少文字就反色多少，只允许文字参与混合；不得在滑块刚接触标签时把整段文字一次性切换颜色，图标 / 徽章也不得跟着反色
- 设置面板内所有二段及以上分段控件与顶栏共用 controls.js 统一分段组件的真实几何与文字局部反色，不得保留“设置专用”的第二套 N 段式实现
- `ⓘ` 渐进帮助统一由 `js/controls.js` 管理：Hover 预览 / 点击固定、自动上下翻转与视口夹取、点击空白 / Esc 关闭；Tooltip 不得溢出屏幕。Toast 使用 `--radius-popover`，禁止胶囊化
- 管理后台 ≤860px 允许从左侧约 36–40px 边缘向右滑打开导航抽屉，抽屉内向左滑关闭；不要扩成页面任意位置右滑
- 对话联网搜索当前**只实现 DeepSeek 官方端点**：能力必须由服务端 Provider 预设 + `api.deepseek.com` 实际 host 共同判定，自定义代理及其他 Provider 一律视为不支持；代码结构可预留未来扩展，但未经逐个验证不得擅自开启。搜索按对话分支保存，新对话沿用上次本地选择，聊天只展示“正在搜索网页 / 已完成搜索”等轻量状态，不渲染工具详情
- 单聊顶栏与“新对话”同一行不显示角色头像，只保留角色名称；「对话模型」折叠箭头收起态朝上、展开态朝下
- 消息未读数为 0 时不显示任何数字气泡；只有 `> 0` 时才显示徽章
- 顶栏常态不显示结构分割线；滚动约 8–16px 后才淡入弱分隔，并使用向内容方向衰减的渐变模糊。手机端可扩大模糊范围，但不得改成明显的整块毛玻璃卡片
- 聊天输入区采用悬浮覆盖式布局：外层不使用整块纯色托底，消息允许从渐变磨砂层下经过；消息底部安全空间必须按“输入区真实高度 + 模糊层向上延伸 + 末条可见缓冲”动态同步，“回到最新”按输入区真实高度上移，不能写死单一高度；最大滚动位置必须能完整露出最后一条消息
- 移动端（≤860px）卡片一律平铺：去背景/边框/阴影/圆角，内容直接铺在页面背景上；可用分隔线组织层级
- 移动端分隔线必须遵循“同一层级只保留一套结构线”：优先只画相邻项之间的 `--border-soft`；禁止父容器首尾线、Section 标题底线、Item 边线在同一层级叠加，连续 Toggle 行也不得每行同时画上/下边形成双线
- “卡片平铺”不适用于明确的交互控件或工作区，例如选中项控件、输入框、自定义 Select、关系图谱画布、消息气泡、Popover 和底部抽屉
- 触摸目标不要为了省空间缩得过小；移动端顶栏 / 消息操作等高频按钮优先保证约 44px 可点击区域
- 设置中的「收起角色信息」是移动端角色面板的空间优化偏好，默认开启：开启后面板顶部默认使用「左头像 + 右名称」紧凑态，不显示身份介绍与状态；点击名称必须基于同一 DOM 连续过渡回完整原排版，避免用两套模板瞬切。用户已明确保存的开/关偏好优先于默认值，关闭后保持完整原排版

### 世界观编辑与活动 UX

- 世界观创建 / 编辑是长表单，必须自动保存本地草稿并提供离开保护；不得因为顶栏切页、返回或误触直接丢失尚未提交到服务器的内容
- 世界观编辑采用渐进式披露：核心设定常驻，历史、势力、关系、知识边界等高级区域按需展开；当某模块尚无成立条件时不要用整块无效表单占据页面
- 历史、IF 时间线、势力、关系、知识边界、可见范围等结构性展开统一使用 `controls.css` 的 `.ctl-collapse` + `aria-expanded` 连续高度动画；禁止用原生 `<details>` 让大段表单瞬切。`ⓘ` 小帮助属于轻量披露，可保留原生即时行为
- 世界观详情的长文本统一按安全 Markdown 渲染；核心世界观设定必须支持可逆、可持久化的收起 / 展开，收起按钮本身不得被一起隐藏
- 世界观「AI 优化格式」只能调整 Markdown 层级、段落、列表、强调与空行，不得增删改事实。所有 AI 帮写 / 优化统一遵循：计费提示（必要时）→ 立即加载弹窗 / 骨架 → 人类可读的可编辑预览 → 用户应用；普通用户界面禁止暴露或要求编辑 JSON
- AI 帮写已有内容优先保留；结构化列表默认追加去重建议，不得整块覆盖用户已经确认的历史、势力或知识数据
- 势力的领袖 / 成员角色属于正式数据，任何世界观编辑保存都不得把未改动成员关系静默清空
- 角色加入世界观必须一次完成：选择角色后立即可编辑世界身份、状态、所属势力与主世界观，不得要求先保存一次再返回填写
- 世界观角色选择器中已经加入的角色必须继续可见但禁止再次勾选，并明确标注「已添加」；移除已有引用使用单独的显式操作，不得通过允许重复选择来兼任移除
- IF 分支创建前必须允许命名 / 说明，创建后必须可编辑 / 删除；删除分支仅级联其子分支，不得影响主时间线，且仍禁止分支扶正或合并回主线
- 顶栏「活动」进入可扩展活动首页，具体活动以卡片 / 入口承载，不得把顶栏入口直接等同于唯一的“世界观历史推演”页面；世界观详情可保留带上下文的活动快捷入口
- 历史推演存在未提交候选历史、日志、状态或候选实体时，切换世界观 / 时间线必须二次确认；自动 N 步开始前明确告知最多 N 次正常计费请求。暂停如果不能取消已发出的当前请求，必须明确显示“当前一步完成后暂停”，不得伪装成立即中止
- 情景聊天不得维护与正式世界观竞争的第二套世界设定。使用“正式世界观（可选）+ 本次场景补充”：正式世界按角色知识边界注入，场景补充只能描述本次地点 / 局势 / 临时条件，冲突时正式世界观优先
- 顶栏 N 段式横向拖拽统一交给 `bindSegmentedControl`；上下文 / 全局顶栏切换只识别明确的纵向手势，方向判定必须先区分横纵意图，禁止让两套手势争抢同一次 pointer。窄屏优先收敛辅助入口，不把主导航改成长横向滚动条

## 管理后台工作台规范

- 管理后台与主应用共享 Design System，但目标是“编辑部工作台”：比主应用更高信息密度，优先展示待处理事项与异常，而不是把所有数字等权铺成仪表盘
- 桌面侧栏按工作域分组：工作台 / 用户与内容 / 安全与治理 / AI 与计费 / 系统；不要重新把十几个入口平铺成同一层级
- 移动端（≤860px）禁止把完整后台导航做成长横向滚动条；使用“当前模块 + 菜单”顶栏，完整分组导航进入抽屉
- 申请审核 / 问题反馈 / 封禁申诉属于收件箱型工作流，优先使用可扫读的记录流而不是传统多列表格；手机端必须纵向重排，操作按钮保持可触达
- 后台总览第一屏先展示待处理工作队列，再展示用户 / 调用等运营指标；待处理项应可直接进入对应工作区
- 永久删除普通用户账号属于最高风险操作，必须严格执行三步确认：风险说明 → 不可逆再次确认 → 当场使用管理员密码或邮箱验证码重新验证。第三步不得复用普通危险操作的 5 分钟确认窗口；服务端必须签发与目标 userId 绑定的一次性删除令牌，用后即废
- 管理员账号与 `Aimo社区` 等系统维护账号不得通过后台删号入口永久删除；前端隐藏 / 禁用入口只是体验层，服务端必须重复校验
- 用户自助注销与管理员永久删号必须共用 `accountDeletionService` 的物理删除链，统一处理公开角色社区接管、文件清理、邮箱黑名单、认证临时数据清理、Socket 断开等副作用，禁止在后台直接裸 `User.destroy()`
- 中文后台标题、表头、Section 标题不要机械套用英文全大写高字距规则；中文以正常字距、字号和留白建立层级

## 骨架屏规范

- 所有真实网络等待状态优先使用骨架屏，不使用孤立的“加载中…”文字或与最终布局无关的转圈；错误态仍使用明确错误信息 + 重试
- 骨架必须和目标页面内容同构：标题、头像、卡片、列表行、表单控件、聊天气泡、管理表格各用对应模板，禁止一个万能矩形骨架覆盖全站
- 登录通过后的启动骨架按当前 URL 路由选择：角色库 / 详情 / 消息 / 搜索 / 创建 / 活动 / 对话使用不同结构；门禁初始化使用与登录表单同构的骨架
- 骨架尺寸应尽量匹配最终内容的行高、间距和列数，避免数据返回后产生明显 Layout Shift；移动端骨架必须遵循移动端真实布局，不照搬桌面排列
- 骨架扫光只承担加载反馈，必须支持 `prefers-reduced-motion`，弱动效模式退化为静态占位
- 新增异步页面或新增一个显著的网络等待区域时，应同步补对应骨架模板；不要先写“加载中…”再留作以后优化

## 历史推演沉浸模式与滚动
- 世界观历史推演的沉浸模式只在网页视口内展开；浏览器 Fullscreen API 必须由独立按钮显式触发，不能进入沉浸时自动请求浏览器全屏。
- 沉浸模式保持现有明/暗主题，不添加脱离主题系统的固定氛围背景；主要内容只保留推演日志、输入与下一步/暂停等必要控制。
- 世界状态面板在沉浸模式默认隐藏，桌面端通过右侧热区靠边唤出，触屏端支持从右边缘手势唤出。
- 自动推演时允许在约 2~3 秒无交互后淡出控制区，鼠标、触摸或键盘交互必须立即恢复；遵守 `prefers-reduced-motion`。
- 推演新增旁白/对话、运行骨架或状态更新时，不得自动把日志滚到顶部或底部；重渲染前记录 `simulationLog` 与活动视图的滚动位置，重渲染后恢复原位置。

## 管理员永久删号兼容性
- 管理员删号必须继续使用三步确认和目标绑定的一次性身份令牌。
- 账号物理删除必须在单一数据库事务内完成；生产 PostgreSQL 的真实外键约束优先于当前 ORM 声明，删除前需兼容历史部署遗留的 `NO ACTION` 外键，避免“验证成功但 User 删除失败”的半完成状态。
